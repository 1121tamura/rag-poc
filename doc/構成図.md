# 構成図

利用者の操作を起点に、各サービスがどう繋がって動くかを図で示す。
仕様書の文章だけでは掴みにくい「実際の流れ」を理解するための資料。

---

## 1. 全体像：どこで何が動いているか

利用者が触るのはブラウザだけで、その裏で4つのサービスが連携している。


```mermaid
flowchart TB
    U["👤 利用者<br/>（運用チーム）"]
    
    subgraph Server["1台のサーバ（EC2 / オンプレLinux）"]
        subgraph C1["コンテナ: streamlit"]
            ST["Streamlit<br/>画面を作る"]
        end
        subgraph C2["コンテナ: api"]
            API["FastAPI<br/>司令塔"]
            EM["BGE-M3<br/>文章→ベクトル変換"]
        end
        subgraph C3["コンテナ: qdrant"]
            QD["Qdrant<br/>ベクトルDB"]
        end
        subgraph C4["コンテナ: ollama"]
            OL["Ollama + Qwen3 8B<br/>文章を書くLLM"]
        end
        SQ[("SQLite<br/>会話履歴")]
    end

    U -->|"① 質問を入力<br/>ブラウザ :8501"| ST
    ST -->|"② HTTPで問い合わせ<br/>:8000"| API
    API -->|"③ 質問をベクトルに"| EM
    EM -->|"④ 似た文書を探す<br/>:6333"| QD
    QD -->|"⑤ 関連チャンク5件"| API
    API -->|"⑥ 文書＋質問を渡す<br/>:11434"| OL
    OL -->|"⑦ 回答を1文字ずつ"| API
    API <-->|"会話の読み書き"| SQ
    API -->|"⑧ 逐次返す"| ST
    ST -->|"⑨ 画面に表示"| U

    style U fill:#D97757,color:#fff
    style Server fill:#FAF9F5,stroke:#A8A296
    style SQ fill:#F0EEE6
```

### それぞれの役割

| サービス | 役割 | たとえるなら |
|---|---|---|
| **Streamlit** | 画面の描画と入力受付 | 受付窓口 |
| **FastAPI** | 検索と生成の手順を統括 | 司令塔 |
| **BGE-M3** | 文章を数値の並び（ベクトル）に変換 | 翻訳機 |
| **Qdrant** | ベクトルを保管し、似たものを高速に探す | 索引付きの書庫 |
| **Ollama + Qwen3 8B** | 渡された文書をもとに日本語の回答を書く | 書き手 |
| **SQLite** | 会話履歴を保存 | 会話のノート |

> **なぜベクトルにするのか**：「発注の承認は誰がやる？」と「承認フローの承認者」は文字列としては
> 一致しないが、意味は近い。文章を数百次元の数値に変換しておくと、**意味の近さを距離として
> 計算できる**ようになる。これがRAGの検索の土台になっている。

## 2. 質問してから回答が出るまで（時系列）

利用者が質問を1回投げたときに、内部で何が順番に起きるか。

```mermaid
sequenceDiagram
    autonumber
    actor U as 👤 利用者
    participant ST as Streamlit
    participant API as FastAPI
    participant SQ as SQLite
    participant EM as BGE-M3
    participant QD as Qdrant
    participant OL as Ollama<br/>(Qwen3 8B)

    U->>ST: 質問を入力
    ST->>API: POST /query<br/>（質問・会話ID・利用者名）
    API->>SQ: この会話は本人のもの？
    SQ-->>API: OK（違えば404で拒否）

    API->>SQ: 直近5往復の履歴を取得

    alt 追加質問（履歴あり）
        API->>OL: 「それは何段階？」を<br/>単独で通じる文に書き換えて
        OL-->>API: 「発注承認フローは何段階？」
    else 初回質問（履歴なし）
        Note over API: 書き換えは不要なので<br/>LLM呼び出しを省略
    end

    API->>EM: 質問をベクトル化<br/>（意味用・単語用の2種類）
    API->>QD: 似た文書を5件ください
    QD-->>API: チャンク5件＋関連度スコア

    Note over API: 関連度チェック<br/>閾値を超えたものがあるか？

    alt 関連する文書あり
        API->>OL: 参照文書＋履歴＋質問
    else 関連する文書なし
        API->>OL: 参照文書を渡さず<br/>「見つからなかった」と伝えるよう指示
    end

    API-->>ST: 【1行目】参照ソース一覧
    ST-->>U: ソースは先に確定（読み込み表示）

    loop 回答を生成しながら
        OL-->>API: 次の数文字
        API-->>ST: 【token行】差分
        ST-->>U: 画面に追記表示
    end

    API->>SQ: 質問と回答を保存

    alt 初回質問だった
        API->>OL: 会話タイトルを作って
        OL-->>API: 「発注承認フロー」
        API->>SQ: タイトルを更新
    end

    API-->>ST: 【最終行】done<br/>（切り詰め通知・タイトル）
    ST-->>U: 参照ソースとタイトルを反映
```

### ポイント3つ

**① ソースを先に返している**
参照ソースは検索が終わった時点で確定する。LLMが書き終わるのを待たずに先へ送ることで、
利用者は「何を根拠に答えようとしているか」を早く知ることができる。

**② 保存は回答が終わってから**
質問を先に保存すると、その質問自身が「履歴」として読み込まれてしまう。
そのため保存は最後にまとめて行う。

**③ タイトル生成も最後**
タイトルを作るにはLLMをもう1回呼ぶ必要がある。先に作ると回答の表示が遅くなるため、
回答が出そろってから作り、会話一覧に後から反映する。

## 3. ハルシネーション（でっち上げ）を防ぐ仕組み

RAGで最も重要な部分。3つの対策が**直列に**効いている。

```mermaid
flowchart TB
    Q["質問"] --> S["Qdrantで検索<br/>上位5件を取得"]
    S --> T{"対策3<br/>関連度は十分か？<br/>dense≧0.55 または sparse≧0.12"}

    T -->|"Yes<br/>関連文書あり"| P1["参照文書をLLMに渡す"]
    T -->|"No<br/>関連文書なし"| P2["参照文書を渡さない"]

    P1 --> L1["対策1<br/>「参照文書のみを根拠に。<br/>無ければ推測せず、<br/>何が無いか具体的に伝える」"]
    P2 --> L2["対策1<br/>「関連文書が無かったと伝え、<br/>具体的な名称を含めて<br/>質問し直すよう案内」"]

    L1 --> A["回答生成"]
    L2 --> A
    A --> V["対策2<br/>参照ソースを画面に表示<br/>（利用者が裏取りできる）"]
    V --> U["👤 利用者"]

    style T fill:#D97757,color:#fff
    style V fill:#F0EEE6
    style U fill:#D97757,color:#fff
```

| 対策 | 内容 | 防ぐもの |
|---|---|---|
| **対策1** プロンプト設計 | 参照文書だけを根拠にさせる | 一般知識で勝手に答えること |
| **対策2** ソース表示 | 根拠にした文書を画面に出す | 利用者が誤りに気づけないこと |
| **対策3** 関連度の閾値 | 関連の薄い文書を最初から渡さない | 無関係な文書を根拠にすること |

> **なぜ閾値だけで完結させないのか**：関連度の判定は完璧ではない。
> 誤って弾けば「あるはずの答えが出ない」、誤って通せば「無関係な文書で答える」。
> どちらも起きうる前提で、3つを重ねて防いでいる。

### 関連度スコアの読み方

検索結果には2種類のスコアがある。**どちらか一方でも閾値を超えれば「関連あり」**と判定する。

| 種類 | 何を測るか | 得意なこと | 閾値 |
|---|---|---|---|
| **dense**（意味） | 文章の意味の近さ | 言い回しが違っても意味が近いものを拾う | 0.55 |
| **sparse**（単語） | 単語の一致度 | 「E-1005」「PO-202608-0001」など固有の文字列 | 0.12 |

開発用サンプル文書での実測値：

| 質問の種類 | dense | sparse |
|---|---|---|
| 文書に答えがある | 0.62〜0.78 | 0.17〜0.29 |
| 文書に答えがない | 0.45〜0.49 | 0.001〜0.07 |
| 挨拶（「こんにちは」） | 0.42〜0.49 | 0.002〜0.007 |

## 4. ドキュメントを取り込むまで（Ingestion）

質問の流れとは**別系統**で、事前に1回行う準備作業。

```mermaid
flowchart LR
    F["📄 docs/配下の<br/>Markdownファイル"] --> D{"前回実行より<br/>新しい？"}
    D -->|No| SKIP["スキップ"]
    D -->|Yes| C["見出し単位で<br/>チャンクに分割"]
    C --> M["メタデータ付与<br/>・文書種別<br/>・ファイルパス<br/>・章タイトル<br/>・更新日時"]
    M --> E["BGE-M3で<br/>ベクトル化<br/>（意味用・単語用）"]
    E --> DEL["同じファイルの<br/>古いチャンクを削除"]
    DEL --> ADD["Qdrantへ登録"]
    ADD --> ST2["実行時刻を記録<br/>.ingestion_state.json"]

    style F fill:#F0EEE6
    style ADD fill:#D97757,color:#fff
```

### なぜ「見出し単位」で切るのか

LLMに渡せる文章量には上限がある。文書を丸ごと渡せないため、あらかじめ小さく切っておき、
質問に関係する部分だけを選んで渡す。このとき**意味のまとまりで切らないと**、
文の途中で切れて内容が通じなくなる。Markdownの見出しは章・節の区切りなので、
そこで切ると内容のまとまりが保たれる。

### 差分取り込みの落とし穴

```mermaid
flowchart TB
    subgraph OK["リセット不要"]
        A1["内容を修正した"] --> A2["古いチャンクを削除して<br/>登録し直す（自動）"]
        B1["ファイルを追加した"] --> B2["新規登録される（自動）"]
    end

    subgraph NG["リセットが必要"]
        C1["ファイルを削除した"] --> C2["⚠️ チャンクが残り続ける<br/>古い内容が回答に出る"]
        D1["ファイル名を変えた"] --> D2["⚠️ 旧名のチャンクが残り<br/>二重にヒットする"]
        E1["更新日時が古いまま<br/>コピーした"] --> E2["⚠️ 取り込まれない"]
    end

    style NG fill:#FFF4F0,stroke:#D97757
    style OK fill:#F0F5F0,stroke:#8AA88A
```

対処法は [`ドキュメント再取り込み手順.md`](ドキュメント再取り込み手順.md) を参照。

## 5. データはどこに保存されるか

コンテナは作り直すと中身が消えるため、消えては困るデータは**ボリューム**に置いている。

```mermaid
flowchart LR
    subgraph V["Dockerボリューム（消えない）"]
        V1[("qdrant_storage<br/>ベクトル化した文書")]
        V2[("app_data<br/>会話履歴のSQLite")]
        V3[("ollama_data<br/>Qwen3 8B（5.2GB）")]
        V4[("hf_cache<br/>BGE-M3（2.2GB）")]
        V5[("ingestion_state<br/>前回取り込み時刻")]
    end

    subgraph H["ホスト側のディレクトリ"]
        H1["docs/<br/>取り込み元の文書<br/>（読み取り専用でマウント）"]
    end

    QD["qdrant"] --- V1
    API["api"] --- V2
    API --- V4
    API --- V5
    API -.読むだけ.- H1
    OL["ollama"] --- V3

    style V fill:#FAF9F5,stroke:#A8A296
    style H fill:#F0EEE6,stroke:#A8A296
```

| 保存先 | 消えたときの影響 | 復旧方法 |
|---|---|---|
| `qdrant_storage` | 検索できなくなる | 再取り込みで復旧可（時間はかかる） |
| **`app_data`** | **過去の会話が失われる** | **復旧不可。要バックアップ** |
| `ollama_data` | LLMが動かない | 再ダウンロードで復旧可 |
| `hf_cache` | 検索・取り込みができない | 再ダウンロードで復旧可 |
| `ingestion_state` | 次回に全件再取り込みされる | 実害は時間だけ |

> **`docker compose down -v` は使わないこと。** `-v` を付けるとボリュームごと消える。
> 会話履歴だけは復旧手段が無い。

## 6. 環境ごとの構成の違い

同じコードを3つの構成で動かしている。

```mermaid
flowchart TB
    subgraph DEV["開発（macOS + Devコンテナ）"]
        D1["api"] -.->|"host.docker.internal"| D2["Ollama<br/>（ホストのmacOS上）"]
        D1 --- D3["qdrant"]
        D4["Streamlit<br/>（VS Codeから手動起動）"]
    end

    subgraph PROD["本番・CPU"]
        P1["api"] --- P2["ollama"]
        P1 --- P3["qdrant"]
        P4["streamlit"] --- P1
    end

    subgraph GPU["本番・GPU"]
        G1["api 🎮"] --- G2["ollama 🎮"]
        G1 --- G3["qdrant"]
        G4["streamlit"] --- G1
    end

    style DEV fill:#F0EEE6
    style PROD fill:#FAF9F5
    style GPU fill:#FFF4F0
```

| 環境 | Composeファイル | Ollamaの場所 | 理由 |
|---|---|---|---|
| 開発 | `docker-compose.yml` + `override.yml` | **ホストのmacOS上** | macOSのコンテナからはGPU（Metal）が使えないため |
| 本番CPU | `docker-compose.prod.yml` | コンテナ | |
| 本番GPU | `prod.yml` + `gpu.yml` | コンテナ（GPU割当） | Linux + NVIDIAならコンテナからGPUを使えるため |

> `docker-compose.override.yml` は**macOSの開発環境専用**。本番に持ち込むと
> Ollamaへの接続先が `host.docker.internal` に書き換わり、繋がらなくなる。
