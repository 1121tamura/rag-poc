# JA運用サポートRAGシステム 仕様書

## 1. 概要

購買システムの各種ドキュメント（設計書・議事録・マニュアル・仕様書）を対象に、
運用チームの問い合わせ対応を支援するRAG（Retrieval-Augmented Generation）システムを構築する。

- 位置づけ：デモアプリ（PoC）。まずは動くものを作り、段階的に拡張する
- 対象範囲：購買システムのドキュメントのみ（他JAシステムは対象外）
- 利用者：運用チーム内の限定人数（社内利用、認証不要）

### フェーズ分け

| フェーズ | スコープ |
|---|---|
| **フェーズ1（今回実装）** | 文書RAG（設計書・議事録・マニュアル・仕様書に対する問い合わせ対応） |
| **フェーズ2（将来実装）** | 業務DBへの自然言語データ分析（Text-to-SQL）。UI上は「データ分析」タブとして先に枠だけ用意し、機能自体はフェーズ2で実装する |

---

## 2. アーキテクチャ全体像

```
[Streamlit UI]
     ↓ HTTP（ストリーミング）
[FastAPI（interfaces層）] ←→ [SQLite（会話履歴）]
     ↓
[RAGService（application層）]
     ↓
[LlamaIndex（オーケストレーション）]
     ↓ 検索                              ↓ 生成
[Qdrant（ベクトルDB）]                  [Ollama（Qwen3 8B）]
     ↑ 格納
[BGE-M3（Embedding）]
     ↑ チャンク分割・メタデータ付与
[Ingestionパイプライン]
     ↑
[購買システムのドキュメント（md/csv/word/excel）]
```

### 設計方針

- DDD + クリーンアーキテクチャを踏襲し、`interfaces / application / infrastructure` の3層に分離する
- 購買システムとは**独立した別プロジェクト**として構築する
  - 理由：LLM推論の重い処理が購買システム本体のリソースを圧迫するのを避けるため
- ただし将来的に購買システム本体からHTTP経由でRAG機能を呼び出す可能性があるため、
  Streamlitから直接RAGロジックを呼ぶのではなく、**FastAPIをインターフェース層として必ず挟む**
- オーバーエンジニアリングを避け、現時点では以下は行わない
  - RAGロジックの独立パッケージ化
  - RAGの別サービス化（マイクロサービス分離）
  - 認証・アクセス制御
  - 自動評価ツール（Ragas等）の導入

## 3. 技術スタック

| レイヤー | 技術 | 選定理由 |
|---|---|---|
| 推論基盤 | Ollama | セットアップが容易、量子化モデル管理がしやすい |
| LLMモデル | Qwen3 8B | 日本語RAGで安定した精度。本番サーバがGPU無し・非ハイスペック前提のため、CPU推論でも現実的なサイズとして8Bに決定（開発・本番共通） |
| オーケストレーション | LlamaIndex | RAG特化、Qdrant/Ollamaと標準対応 |
| ベクトルDB | Qdrant（セルフホスト、Docker） | Rust実装で高スループット、メタデータフィルタリングが強力、Apache 2.0で無料 |
| Embeddingモデル | BGE-M3 | 長文（最大8192トークン）対応、dense/sparse両対応でハイブリッド検索が可能 |
| バックエンド | FastAPI | 非同期I/OがRAGの処理特性と噛み合う、Pydanticネイティブ |
| UI | Streamlit | チームに使用経験あり、ChatGPT風のストリーミング表示に対応 |
| チャンク分割 | 見出し単位（Markdownは`MarkdownNodeParser`） | 文書の構造（章・節）を保ったまま検索文脈を維持するため |

## 4. ディレクトリ構成（ドキュメント側）

サーバ内ディレクトリから直接読み込む。文書種別ごとにディレクトリを分け、
`document_type` はこのディレクトリ構造から自動判定する。

```
docs/
├── specs/       # 仕様書
├── design/      # 設計書
├── minutes/     # 議事録
└── manuals/     # マニュアル
```

対応ファイル形式：`.md`, `.csv`, `.docx`, `.xlsx`

---

## 5. メタデータスキーマ

各チャンクに以下のメタデータを付与し、Qdrantに格納する。

| 項目 | 型 | 説明 | 取得方法 |
|---|---|---|---|
| `document_type` | string | 設計書/議事録/マニュアル/仕様書の区分 | ディレクトリ構造から自動判定 |
| `file_path` | string | 元ファイルのパス。差分更新・削除時のキーとしても使用 | 自動 |
| `chapter_title` | string（nullable） | 章・節タイトル。議事録等では無い場合もある | Markdownは`MarkdownNodeParser`で自動、Word/Excelは要検討 |
| `file_format` | string | md / csv / word / excel | 拡張子から自動 |
| `updated_at` | datetime | 最終更新日時 | ファイルのmtimeから自動取得 |
| `version` | string（nullable） | 将来のバージョン管理拡張に備えて保持。現時点では必須運用はしない | ファイル内記載があれば抽出 |

**対象外とする項目**
- `system_name`：購買システムのみが対象のため不要
- `access_level`：アクセス制御を行わないため不要

**確定した値（実装時に決定）**
- `document_type`：`docs/`配下のディレクトリ名をそのまま使用する（`specs` / `design` / `minutes` / `manuals`）

## 6. Ingestionパイプライン

### 6.1 処理フロー

```
① 読み込み（対象ディレクトリからファイル読み込み）
     ↓
② チャンク分割（見出し単位。Markdown以外は形式に応じたパーサー）
     ↓
③ メタデータ付与（document_type / file_path / chapter_title / file_format / updated_at）
     ↓
④ Embedding生成（BGE-M3）
     ↓
⑤ Qdrantへ格納
```

Qdrantのコレクション名は`documents`とする。

### 6.2 実行方式

- **手動実行**：ドキュメントが更新されたタイミングで、担当者がコマンドを実行する（自動トリガーなし）
- **差分処理**：全件ではなく、変更があったファイルのみを処理対象とする
  - 判定方法：ファイルの更新日時（mtime）と前回Ingestion実行時刻を比較する
  - 前回実行時刻の記録は簡易的な方法で可（例：ローカルのJSONファイルに保存する程度でよい。厳密な設計は不要）
  - 確定：`.ingestion_state.json`に`{"last_run": "<ISO8601形式の時刻>"}`の形式で保存する。
    保存先は既定でプロジェクトルート直下とし、環境変数`INGESTION_STATE_FILE`で変更できる
    （本番はコードをイメージに焼き込むため、Dockerボリューム側を指定する。10.2参照）

### 6.3 重複防止

以下の方式で重複を防ぐ。

1. 対象ファイルに対応する既存チャンクを、Qdrant上で `file_path` をキーにフィルタして**削除**する
2. 新しい内容でチャンク分割・Embedding生成を行う
3. Qdrantに**新規登録**する

> 決定論的ID生成による重複判定ではなく、「ファイル単位で削除してから登録し直す」方式を採用する。
> チャンク数が変動した場合（章立ての変更等）でも、古いチャンクが残留しない点がメリット。

### 6.4 対応が必要な文書形式

| 形式 | 想定用途 | 備考 |
|---|---|---|
| Markdown（.md） | 仕様書 | `MarkdownNodeParser`で見出し単位分割 |
| Word（.docx） | 設計書・マニュアル | LlamaIndexの`DocxReader`等を使用。チャンク分割方法は別途検討が必要 |
| Excel（.xlsx） | 一覧表・パラメータ表 | 行/シート単位での扱いを検討 |
| CSV（.csv） | 議事録・Q&A集等 | 行単位でのチャンク化を想定 |

## 7. クエリ・応答フロー

### 7.1 処理フロー

```
① Streamlitでユーザーが質問を入力
② FastAPIの /query エンドポイントへHTTPリクエスト
③ RAGServiceが質問を受け取り、LlamaIndex経由でQdrantを検索
④ 検索結果（該当チャンク）をコンテキストとしてOllama（Qwen3 8B）へ渡す
⑤ LLMが回答を生成し、トークン単位でストリーミング返却
⑥ Streamlit側がChatGPTのように逐次表示
⑦ 回答と合わせて、参照した文書（ソース）を画面に表示
```

### 7.2 ストリーミング応答

- FastAPI側：`StreamingResponse` を用いてトークンを逐次返却する
- Streamlit側：`st.write_stream` を用いて逐次表示する
- LlamaIndex側：ストリーミング対応のクエリAPI（例：`astream_chat`系）を使用する
- レスポンス形式（確定）：NDJSON（1行1JSON）とする。行の種類は以下の3つ。

  | 順序 | 形式 | 内容 |
  |---|---|---|
  | 1行目 | `{"type": "sources", "sources": [...]}` | 参照ソース。検索完了時点（LLM生成前）で確定しているため先頭で返せる |
  | 2行目以降 | `{"type": "token", "content": "..."}` | 回答トークンの差分 |
  | 最終行 | `{"type": "done", "is_history_trimmed": bool, "is_query_rewritten": bool, "title": str\|null}` | 付随情報 |

- `done`行を末尾に置く理由：会話タイトルは回答生成の完了後に生成するため先頭では返せない（7.4）。
  また、履歴の切り詰め通知や指示語の案内は、回答本文の後に表示する方が読み手の妨げにならない。
  `title`は初回質問時のみ値が入り、それ以外は`null`とする

### 7.3 ハルシネーション対策（必須要件）

以下の対策を組み合わせて実装する。

1. **プロンプト設計**
   - システムプロンプトに「参照文書に情報がない場合は推測で回答しない」旨を明記する
   - 対策3の閾値判定により、参照文書を渡す場合と渡さない場合が生じるため、プロンプトは2種類とする
   - 「分かりません」の一言で終わらせない。利用者が次に何をすればよいか分からなくなるため、
     必ず具体的な補足（何が記載されていないか、どう質問し直せばよいか）を伴わせる
   - 確定した文言（参照文書を渡す場合）：
     ```
     あなたは購買システムのドキュメントに基づいて質問に回答するアシスタントです。
     挨拶や世間話には自然に応答して構いません。
     ただし、購買システムに関する質問については、以下の参照文書の情報のみを根拠に回答してください。
     参照文書に答えが書かれていない場合は、推測で回答せず、参照文書のどこまでが分かっていて
     何が記載されていないのかを具体的に伝えたうえで、どう質問し直せば見つかりそうかを添えてください。
     ```
   - 確定した文言（対策3により参照文書を渡さない場合）：
     ```
     あなたは購買システムのドキュメントに基づいて質問に回答するアシスタントです。
     今回の質問に関連する社内文書は見つかりませんでした。
     挨拶や世間話には自然に応答してください。
     購買システムに関する質問の場合は、関連する文書が見つからなかったことを伝えたうえで、
     機能名・エラーコード・帳票名など具体的な名称を含めて質問し直すよう案内してください。
     推測による回答や、文書に存在しない内容の説明は絶対にしないでください。
     ```
   - 挨拶・世間話は対策3の閾値で弾かれ後者のプロンプトに入るため、後者にも自然な応答を明記している
2. **回答根拠の明示**
   - 回答と合わせて、参照した文書のソース（ファイル名・章タイトル等）を必ず表示する
   - 利用者が裏取りできる状態にする
3. **検索結果の関連度チェック**
   - 検索でヒットしたチャンクの関連度が閾値を下回る場合、参照文書をLLMに渡さず、
     関連する文書が見つからなかった旨と質問の言い換え方を案内する（対策1の後者のプロンプト）
   - **融合後のスコアは閾値判定に使えない**。LlamaIndexのQdrant連携が既定で用いる
     `relative_score_fusion` は、dense・sparse各結果セット内でスコアを0〜1に正規化してから
     合成するため、`node.score` は結果セット内の相対値であり関連度の絶対値ではない。
     実測でも、無関係な質問の1位が必ず0.5以上になった
   - そのため、カスタム融合関数（`hybrid_fusion_with_raw_scores`）で融合前の生スコアを
     ノードのメタデータに保持し、そちらで判定する
   - **判定条件（確定）**：dense ≥ 0.55 **または** sparse ≥ 0.12
     - denseとsparseは得意な検索語が異なる（8章）ため、片方の指標だけに依存すると
       その指標が苦手なクエリ型を誤って弾く。どちらかが閾値を超えていれば関連ありとみなす
     - 誤って弾く方（関連文書があるのに見つからないと返す）は実害が大きい一方、
       誤って通す分は対策1のプロンプトが受け止める。対策は3つの組み合わせで機能させる設計とする
   - **閾値の測定根拠**（開発用サンプル文書45チャンク・15問での1位スコア）：

     | グループ | dense | sparse |
     |---|---|---|
     | 関連あり（7問） | 0.6185 〜 0.7811 | 0.1741 〜 0.2904 |
     | 無関係（5問） | 0.4485 〜 0.4924 | 0.0010 〜 0.0654 |
     | 挨拶（3問） | 0.4190 〜 0.4942 | 0.0018 〜 0.0070 |

     両群の中間を閾値とした。15問すべてで期待通りの判定となることを確認済み
   - 状態：実装済み。ただし閾値は開発用サンプル文書での暫定値であり、
     実際の購買システム文書を投入した後に人手レビューで見直す（9章）

### 7.4 会話履歴・マルチターン対話

過去の会話を見返せるようにし、かつ直前のやり取りを踏まえた追加質問（「それはいつ？」等）にも
回答できるよう、会話履歴をサーバ側に永続化する。

#### 保存方式

- SQLite（`data/history.db`）に保存する。標準ライブラリの`sqlite3`で扱えるため依存追加は不要
- Streamlitから直接DBを読み書きせず、必ずFastAPI経由とする
  - 理由：将来認証を追加した際、「この会話を読んでよいか」の判定はサーバ側でしか行えないため。
    UIが直接DBを触る構成にすると、認証追加時に永続化層ごと移設することになる

#### スキーマ

**conversations**

| 項目 | 型 | 説明 |
|---|---|---|
| `id` | TEXT（PK） | UUID |
| `user_id` | TEXT | 利用者識別子（後述） |
| `title` | TEXT | 会話タイトル。初回質問からLLMが生成する |
| `created_at` | TEXT | 作成日時（ISO8601） |
| `updated_at` | TEXT | 最終更新日時。一覧の並び順に使用する |

**messages**

| 項目 | 型 | 説明 |
|---|---|---|
| `id` | TEXT（PK） | UUID |
| `conversation_id` | TEXT（FK） | 所属する会話 |
| `role` | TEXT | `user` / `assistant` |
| `content` | TEXT | 本文 |
| `sources` | TEXT（nullable） | 参照ソースのJSON。過去の会話を開いた際も再表示するために保存する |
| `created_at` | TEXT | 作成日時（ISO8601） |

インデックス：`conversations(user_id, updated_at DESC)`、`messages(conversation_id, created_at)`

#### 利用者の識別（認証の後付けを前提とした設計）

認証・アクセス制御は現時点でスコープ外（13章）だが、後から追加できる形にしておく。

- 「誰か」を知っているのは、FastAPIの依存関数 `get_current_user_id()` ただ1つとする
  - 現在：リクエストヘッダ `X-User-Id` を読む（UIがサイドバーで入力された利用者名を送る）
  - 認証追加後：同じ関数が `Authorization` ヘッダのJWTから `sub` を取り出すよう差し替える
  - APIのパス・スキーマ・DBスキーマはいずれも変更不要
- `user_id` は表示名と分離し、名前空間付きの識別子とする
  - 現在：`local:<入力された名前>` ／ 認証追加後：`oidc:<sub>`
  - 接頭辞により、移行時のID衝突を防ぎ、暫定IDかどうかを判別できる
  - 表示名をそのままキーにすると、改名や認証移行で履歴のひも付けが壊れるため分離する
- 現状の識別は自己申告であり、なりすまし防止は認証追加時の対応とする

#### 処理フロー

```
① UIは会話IDとともに質問を送る（会話全文は送らない）
② サーバが該当会話の履歴を読み出す
③ 履歴がある場合、LLMで質問を「単独で意味の通る検索クエリ」に書き換える（query rewriting）
   　例：「それはいつ？」→「発注承認フローの開始時期はいつか」
   　初回質問（履歴なし）は書き換えをスキップし、LLM呼び出しを節約する
   　履歴で解決できない指示語は推測で補完せず、質問文をそのまま検索に渡す
④ 書き換え後のクエリでQdrantを検索
⑤ 参照文書＋直近5往復の履歴をプロンプトに含めて回答を生成
⑥ 質問・回答（＋ソース）をSQLiteに保存する
```

- プロンプトに含める履歴は**直近5往復**とする
  - 理由：Qwen3 8Bのコンテキスト長と、CPU推論での応答速度のバランス
- 会話タイトルは初回質問時にLLMで生成する

#### 実装時に確定した事項

- **会話の作成タイミング**：`POST /conversations` はUIで最初の質問を送る直前に呼ぶ。
  「新しい会話」ボタンを押しただけでは作成しない（押しただけで質問しなかった場合に、
  空の会話が一覧に残るのを避けるため）
- **タイトルの扱い**：作成時は仮の値（`新しい会話`）を入れ、初回質問への回答が
  出そろった後にLLMで生成した値へ差し替える
  - 回答生成の前にタイトルを作ると、LLM呼び出しが1回増えた分だけ初回応答が遅くなるため
  - タイトルは20文字以内。LLMが空や長文を返した場合は字数で切り詰め、質問文の先頭にフォールバックする
- **書き換えの適用範囲**：query rewritingの結果は**検索にのみ**使用し、
  プロンプトに渡す質問は原文のままとする（プロンプトには履歴も同梱されるため文脈が通る）
- **他人の会話への書き込み防止**：`/query` で `conversation_id` を受け取った際、
  その会話が要求元の利用者のものかを確認し、そうでなければ404を返す
  - 履歴の読み出しは `user_id` で絞られているため、書き込み側だけ無防備になるのを防ぐ
  - 認証自体はスコープ外（13章）であり、`X-User-Id` は自己申告のため、
    なりすまし防止にはならない点は変わらない
- **保存のタイミング**：質問・回答ともに回答のストリーム完了後に保存する
  - 質問を先に保存すると、その質問自身が履歴として読み出されてしまうため
  - 生成の途中でクライアントが切断した場合、その往復は保存されない（PoCとして許容する）

#### トークン予算と履歴の切り詰め

Ollamaの既定コンテキスト長は4,096トークンで、`qwen3:8b`本来の40,960より大幅に小さい。
超過分は警告もエラーもなく捨てられるため、以下の対応を行う。

- `ollama_client.py`で`context_window=8192`を明示指定し、既定値に依存しない
- プロンプト（システムプロンプト＋参照文書＋履歴＋質問＋回答生成枠）が予算を超える場合、
  古い往復から順に落とす
  - 切り詰めは往復単位で行う（アシスタントの回答のみが残る状態を作らない）
  - トークン数は「1文字＝1トークン」として概算する。安全側に多く見積もることで、
    あふれて参照文書やシステムプロンプトが失われる事態を防ぐ
- 切り詰めが発生した場合はUIに通知する

測定値（開発環境、Ollama 0.17.6 / `qwen3:8b`）：
日本語は約1.34文字/トークン、プロンプト評価は約32トークン/秒。
履歴を1,000トークン増やすと初回応答が約31秒遅くなる。

#### 指示語が解決できない場合の扱い

query rewritingのプロンプトに「履歴で解決できない指示語は推測で補完せず、
質問文をそのまま返す」旨を明記する。

- 理由：推測で補完すると、無関係な文書を根拠にした体裁の整った回答が返り、
  参照ソースも表示されるため利用者が誤りに気づけない。
  事実の捏造ではなく「別の質問への正しい回答」であるため、7.3の対策では検知できない
- 書き換えが行われなかった場合、UIは「分かりません」で終わらせず、
  具体的な名称を含めて質問し直すよう案内する

#### APIエンドポイント

| メソッド | パス | 用途 |
|---|---|---|
| GET | `/conversations` | 利用者の会話一覧（`updated_at` 降順） |
| POST | `/conversations` | 会話の新規作成 |

- サイドバーで利用者名を入力し、`X-User-Id` ヘッダとして送信する

## 8. 検索方式

- **メタデータフィルタリング**：`document_type` 等でQdrantの検索範囲を絞り込む
- **ハイブリッド検索**：ベクトル類似度検索（意味的な近さ）とキーワード検索（完全一致）を組み合わせる（フェーズ1から採用）
  - 理由：エラーコードや型番など、固有名詞・完全一致が重要な検索語に対応するため。購買システムのドキュメントには型番・エラーコードの記載が多いと想定されるため、まずdenseのみで様子を見るのではなく最初から導入する
  - BGE-M3はdense/sparse両方のembeddingを出力できる。ただしsparseベクトルの取得には`FlagEmbedding`ライブラリ（`BGEM3FlagModel`）が必要（LlamaIndexの標準Embedding連携はdenseのみのため、sparse部分は別途配線する）
- **スコアの融合方式**：LlamaIndexのQdrant連携が既定で用いる`relative_score_fusion`を使用する。
  ただし融合後のスコアは結果セット内で正規化された相対値であり、関連度の絶対値ではない。
  そのため7.3の閾値判定に使えるよう、カスタム融合関数で**融合前の生スコア**（dense・sparseそれぞれ）を
  ノードのメタデータに保持する。検索の実行回数は1回のまま変わらない
- **Embeddingモデルの常駐**：BGE-M3は読み込みに時間がかかる（約2.2GB）ため、
  プロセス内で1度だけ読み込んでキャッシュする。dense用とsparse用で2つ常駐し、合計約4.5GBを消費する
- **類似度検索の上位取得件数（`top_k`）**：5件を初期値とする（人手レビューで調整する前提。仕様として厳密に固定するものではない）

## 10. デプロイ・インフラ

### 10.1 環境の段階

1. **開発**：Devコンテナ内で構築・動作確認（CPU、メモリ16GB想定）
2. **本番**：既存のWebアプリ（購買システム）が稼働しているLinuxサーバ上で動作させる
   - GPUは無い想定
   - サーバスペックは非ハイスペック（詳細スペックは未確定）

### 10.2 構成要素のコンテナ化

- Qdrant：Docker公式イメージ（`qdrant/qdrant`）を使用
- FastAPIアプリ・Streamlit：Dockerコンテナ化
- Ollama：ホスト実行 or コンテナ化は環境に応じて判断する
- 接続先はすべて環境変数（`QDRANT_HOST`/`QDRANT_PORT`/`OLLAMA_BASE_URL`/`API_BASE_URL`）で
  切り替え可能とし、環境が変わってもComposeファイルの変更のみで対応できるようにする

#### 確定：環境ごとのCompose構成

開発用と本番用でファイルを分ける。開発用の`docker-compose.yml`は`api`を`sleep infinity`で
待機させVS Codeから中に入って作業する構成のため、本番ではそのまま使えない。

| 環境 | 使用するファイル | 構成 |
|---|---|---|
| 開発（Devコンテナ） | `docker-compose.yml` + `docker-compose.override.yml` | `api`/`qdrant` の2コンテナ。Ollamaは**ホストのmacOS上で実行**する |
| 本番（CPU） | `docker-compose.prod.yml` | `api`/`streamlit`/`qdrant`/`ollama` の4コンテナ |
| 本番（GPU） | `docker-compose.prod.yml` + `docker-compose.gpu.yml` | 上記に加え、`api`と`ollama`にGPUを割り当てる |

- **開発環境でOllamaをホスト実行する理由**：macOSのコンテナからはMetal（GPU）にアクセスできず、
  コンテナ内で動かすとCPU実行になるため。`docker-compose.override.yml`が`OLLAMA_BASE_URL`を
  `host.docker.internal`に上書きし、`.devcontainer/devcontainer.json`の`runServices`で
  `ollama`コンテナを起動対象から除外している
  - `docker-compose.override.yml`は**macOSの開発環境専用**である。本番サーバに持ち込むと
    Ollamaへ接続できなくなるため、本番では常に`-f`でファイルを明示して起動する
- **Linux + NVIDIA環境ではコンテナからGPUを利用できる**ため、本番ではOllamaもコンテナで動かす
  （NVIDIA Container Toolkitの導入が必要）
- **Embeddingの実行デバイス**は環境変数`EMBEDDING_DEVICE`で切り替える（既定`cpu`）。
  GPUで動かすにはCUDA版のPyTorchが必要で、`pyproject.toml`のインデックス指定を差し替える
  - Ollamaは自前のランタイムを持つためこの設定と無関係にGPUを使う。
    そのため「LLM推論だけ先にGPU化し、Embeddingは後で」という段階的な移行も可能

デプロイの具体的な手順は以下を参照。

- [`デプロイ手順_AWS_EC2_GPU.md`](デプロイ手順_AWS_EC2_GPU.md)
- [`デプロイ手順_オンプレミス.md`](デプロイ手順_オンプレミス.md)
- [`ドキュメント再取り込み手順.md`](ドキュメント再取り込み手順.md)

### 10.3 留意事項

- 本番サーバはWebアプリ（購買システム）と共存させる想定のため、
  LLM推論の負荷がWebアプリ本体を圧迫しないよう、リソース配分には注意が必要
  （厳密なリソース制限の設計は今回のデモ段階では不要。今後の検討事項とする）

## 12. データ分析機能（Text-to-SQL）※フェーズ2

> **本セクションはフェーズ2のスコープであり、フェーズ1（今回の実装）では対象外とする。**
>
> **確定：フェーズ1では「データ分析」タブを用意しない。** 理由は2点。
> フェーズ2の実装時にどのみちUI構造を見直すことになり、それまで押しても
> 「実装予定」としか出ないタブを置く実益が小さいこと。
> および`st.chat_input`はタブ等のコンテナ内に置くと画面下部への自動固定が効かないため、
> 枠を用意するだけでも現状のUI構造に手を入れる必要が生じること。
>
> 以下は将来実装時の方針として仕様書に残す。

文書RAGとは別軸の機能として、購買システムの業務データに対する自然言語での分析機能を追加する。

### 12.1 概要

```
[Streamlit UI（データ分析タブ）]
     ↓ 質問（自然言語、例:「先月の発注件数は？」）
[FastAPI（/analyze エンドポイント、文書RAGとは別のルート）]
     ↓
[SQLQueryService（文書RAGのRAGServiceとは別サービス）]
     ↓
[LLMがテーブルスキーマを見てSQLを生成]
     ↓
[生成SQLを実行（読み取り専用DB）]
     ↓
[実行結果をLLMが自然言語で要約して返却]
```

- LlamaIndexの`NLSQLTableQueryEngine`相当の仕組みを利用する想定
- 接続先DBはPostgreSQLまたはMySQL（未確定）。SQLAlchemy経由での実装のため、
  どちらでも実装方針自体は大きく変わらない

### 12.2 安全性要件（必須）

- **読み取り専用に限定する**
  - DB接続ユーザーはSELECT権限のみを付与する
  - 生成されたSQLをパースし、`SELECT`以外の文（`INSERT`/`UPDATE`/`DELETE`/`DROP`等）は実行前に拒否する
  - クエリのタイムアウト・返却行数の上限を設定し、重い集計クエリが実行されても業務影響を抑える
- **本番DBには直接接続しない**
  - 読み取り専用のレプリカDB、または定期同期される分析用DBを別途用意し、そちらに接続する
  - 分析クエリの負荷特性は通常のトランザクション処理と異なるため、本番DBへの直接接続は避ける

### 12.3 スキーマ設計

- 全テーブルをLLMに見せるのではなく、**分析対象として意味のあるテーブルのみを絞り込んで**スキーマ情報を渡す
- 対象テーブルの選定は別途行う（購買・発注・取引先マスタ等、想定される分析ニーズに応じて選定）

### 12.4 文書RAGとの統合方法

- **画面（UI）上でタブ等により明示的にモードを分離する**（「文書検索」タブと「データ分析」タブ）
- 質問文の内容から自動判定してRAG/SQLに振り分けるルーティング層は、今回は採用しない
  - 理由：判定用の追加LLM呼び出しが必要になりレイテンシ・コストが増える上、誤判定のリスクとフォールバック設計が必要になり、デモ段階では過剰な複雑さになるため
  - 将来的に1つのチャット窓口で自然に両方使いたいニーズが強まった場合に、ルーティング層の導入を検討する
- バックエンドは `/query`（文書RAG）と `/analyze`（SQL分析）の2つのエンドポイントに分離する
