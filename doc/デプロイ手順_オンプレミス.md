# デプロイ手順：オンプレミス環境

購買システムRAGを、社内のLinuxサーバへデプロイする手順。

> **前提**：仕様書10.1では「既存のWebアプリ（購買システム）が稼働しているLinuxサーバ上で動作させる」
> 「GPUは無い想定」とされている。ただし実際のサーバスペックは未確定（仕様書14章）のため、
> この手順書は **GPUの有無を最初に判定し、そこから分岐する** 構成にしている。
>
> 本番用の設定ファイル（`docker-compose.prod.yml` / `docker-compose.gpu.yml`）は用意済み。
> 3章はその使い分けと、オンプレ特有の準備をまとめている。

---

## 0. AWS版との違い

[`デプロイ手順_AWS_EC2_GPU.md`](デプロイ手順_AWS_EC2_GPU.md) と重複する部分は多いが、
オンプレ特有の論点が3つある。

| 論点 | 内容 |
|---|---|
| **既存システムとの同居** | 購買システム本体と同じサーバで動く。ポート競合とリソースの奪い合いに注意が必要（仕様書10.3） |
| **インターネット接続の制限** | 社内サーバは外部への通信が制限されていることが多い。モデルの事前取得が必要になる場合がある |
| **GPUの有無が未確定** | CPUだけでも動くが、応答速度が大きく変わる。1章で判定する |

## 1. サーバの状態を確認する

作業を始める前に、以下をすべて確認する。**ここでの判定結果によって、後の手順が分岐する。**

### 1.1 GPUの有無

```bash
nvidia-smi
```

| 結果 | 判定 | この後の進み方 |
|---|---|---|
| GPU名とメモリ量が表示される | **GPUあり** | 3.4「GPU構成」を採用 |
| `command not found` | **GPUなし（CPU運用）** | 3.4「CPU構成」を採用 |

### 1.2 メモリの空き

```bash
free -h
```

**必要なメモリの内訳**（CPU運用の場合）：

| 用途 | 必要量 |
|---|---|
| Qwen3 8B（4bit量子化） | 約5.2GB |
| BGE-M3（dense用・sparse用の2つが常駐） | 約4.5GB |
| Qdrant + FastAPI + Streamlit | 約1〜2GB |
| **RAGシステムの合計** | **約11〜12GB** |

購買システム本体が使っている分を差し引いて、**16GB以上の空き**があることが望ましい。
足りない場合は5章「リソース制限」を必ず設定すること。

### 1.3 ディスクの空き

```bash
df -h
```

モデル約8GB＋Dockerイメージ約5GB＋ドキュメントとベクトルデータで、**最低30GB**の空きが必要。

### 1.4 ポートの空き

購買システム本体と衝突しないか確認する。

```bash
ss -tlnp | grep -E ':(8000|8501|6333|11434)'
```

**何も表示されなければ空いている。** 使用中のポートがあれば、3.4の compose ファイルで
`ports` の左側（ホスト側）の番号を変更する。例：`"18501:8501"` とすれば
ブラウザからは18501番でアクセスすることになる。

### 1.5 外部通信の可否

```bash
# Dockerイメージの取得元に到達できるか
curl -I https://registry-1.docker.io/v2/ --max-time 10

# モデルの取得元に到達できるか
curl -I https://huggingface.co --max-time 10
curl -I https://ollama.com --max-time 10
```

**いずれかが失敗する場合は、2章「オフライン環境向けの事前準備」が必要になる。**

### 1.6 Docker の有無

```bash
docker --version
docker compose version
```

未導入の場合、社内のパッケージ管理方針に従って導入する。
インターネット制限がある環境では、社内リポジトリ経由の導入になることが多い。

## 2. オフライン環境向けの事前準備

1.5で外部通信ができなかった場合のみ実施する。
**インターネットに接続できる別のマシン**で以下を用意し、ファイルとして持ち込む。

### 2.1 Dockerイメージを持ち出す

```bash
# 接続できるマシンで実行
docker pull qdrant/qdrant:latest
docker pull ollama/ollama:latest
docker pull python:3.11-slim

docker save qdrant/qdrant:latest ollama/ollama:latest python:3.11-slim -o rag-images.tar
```

`rag-images.tar` を対象サーバへ運び、読み込む：

```bash
docker load -i rag-images.tar
```

### 2.2 LLMモデルを持ち出す

接続できるマシンでOllamaを動かしてモデルを取得し、保存ディレクトリごとコピーする。

```bash
# 接続できるマシンで実行
docker run -d --name ollama-tmp -v ollama_tmp:/root/.ollama ollama/ollama:latest
docker exec ollama-tmp ollama pull qwen3:8b

# ボリュームの中身をtarに固める
docker run --rm -v ollama_tmp:/data -v $(pwd):/backup alpine \
  tar czf /backup/ollama-qwen3.tar.gz -C /data .
```

対象サーバで展開する：

```bash
docker volume create ollama_data
docker run --rm -v ollama_data:/data -v $(pwd):/backup alpine \
  tar xzf /backup/ollama-qwen3.tar.gz -C /data
```

### 2.3 Embeddingモデル（BGE-M3）を持ち出す

```bash
# 接続できるマシンで実行（約2.2GB）
pip install huggingface_hub
python -c "from huggingface_hub import snapshot_download; snapshot_download('BAAI/bge-m3', local_dir='./bge-m3')"

tar czf bge-m3.tar.gz bge-m3/
```

対象サーバで、`hf_cache` ボリュームへ展開する。展開先の階層は
HuggingFaceのキャッシュ形式（`models--BAAI--bge-m3/`）に合わせる必要があるため、
**実際に一度オンラインでダウンロードしたキャッシュディレクトリごと持ち出す方が確実**である。

```bash
# 接続できるマシンで、キャッシュごと固める方が失敗しにくい
tar czf hf-cache.tar.gz -C ~/.cache/huggingface .
```

### 2.4 Pythonパッケージを持ち出す

`uv sync` はビルド時にPyPIへアクセスする。オフラインの場合は、
接続できるマシンでホイールを一括ダウンロードして持ち込み、そこからインストールする。

```bash
# 接続できるマシンで実行
pip download -r <(uv export --no-dev --format requirements-txt) -d ./wheels
tar czf wheels.tar.gz wheels/
```

Dockerfile を、持ち込んだホイールを使う形に変更する（3.3参照）。

## 3. ファイルの準備

### 3.1 ソースコードの配置

```bash
git clone <リポジトリのURL> /opt/rag-support-system
cd /opt/rag-support-system
```

Gitが使えない環境では、zipで持ち込んで展開する。

### 3.2 `docker-compose.override.yml` を削除する

**必ず確認すること。** このファイルは macOS の開発環境専用で、
`OLLAMA_BASE_URL` を `host.docker.internal` に書き換えてしまう。
本番サーバに存在すると Ollama に接続できなくなる。

```bash
rm -f docker-compose.override.yml
```

（本手順では常に `-f docker-compose.prod.yml` を明示するため自動読み込みはされないが、
事故防止のため削除しておく方が安全である。）

### 3.3 【用意済み】`Dockerfile`

`Dockerfile` は本番用にソースコードをイメージへ焼き込む形になっている。変更は不要である。

> **オフライン環境の場合のみ**、`RUN uv sync --frozen --no-dev` を
> 持ち込んだホイールからのインストールに置き換える：
> ```dockerfile
> COPY wheels/ /wheels/
> COPY requirements.txt ./
> RUN pip install --no-index --find-links=/wheels -r requirements.txt
> ```

### 3.4 【用意済み】本番用のCompose設定

本番用のCompose設定はリポジトリに用意済みで、2本立てになっている。

| ファイル | 役割 |
|---|---|
| `docker-compose.prod.yml` | 本番の基本構成（CPU前提）。api・streamlit・qdrant・ollama の4サービス |
| `docker-compose.gpu.yml` | GPU用の上書き。api と ollama にGPU割り当てを追加し、`EMBEDDING_DEVICE=cuda` にする |

**1.1の判定結果に応じて、起動コマンドを使い分ける。**

#### CPU構成（GPUなしの場合）

```bash
docker compose -f docker-compose.prod.yml up -d
```

追加のファイル変更は不要である。`EMBEDDING_DEVICE` は既定の `cpu` が使われる。

#### GPU構成（GPUありの場合）

```bash
docker compose -f docker-compose.prod.yml -f docker-compose.gpu.yml up -d
```

**あわせて以下の準備が必要**である。

1. **NVIDIA Container Toolkit の導入**（AWS版の3.3を参照）。
   未導入だと `could not select device driver "nvidia"` で起動に失敗する
2. **PyTorchをCUDA版へ差し替え**（AWS版の4.3を参照）。
   `pyproject.toml` の該当箇所を入れ替えて `uv lock` を実行する。
   これを行わないと `EMBEDDING_DEVICE=cuda` にしてもEmbeddingはGPUで動かない

> **Ollama（LLMの回答生成）はPyTorchの設定と無関係にGPUを使う。**
> まずGPU割り当てだけ行い、PyTorchはCPU版のままにして「LLM推論だけGPU化する」段階的な進め方もできる。

#### ポートが埋まっていた場合

1.4で8501番が使用中だった場合は、`docker-compose.prod.yml` の `streamlit` サービスの
`ports` の左側（ホスト側）を変更する。例：`"18501:8501"`。

### 3.5 【用意済み】デバイスの切り替え

`src/infrastructure/llama_index_factory.py` は環境変数 `EMBEDDING_DEVICE` で
CPU／GPUを切り替えられるようにしてある（既定は `cpu`）。
将来GPUサーバへ移行する際も、コード変更は不要である。

## 4. デプロイの実行

```bash
cd /opt/rag-support-system

# ビルド
docker compose -f docker-compose.prod.yml build

# 起動
docker compose -f docker-compose.prod.yml up -d

# 状態確認
docker compose -f docker-compose.prod.yml ps
```

### LLMモデルの取得（初回のみ）

オンラインの場合：

```bash
docker compose -f docker-compose.prod.yml exec ollama ollama pull qwen3:8b
```

オフラインの場合は2.2で持ち込み済みのため不要。以下で確認する：

```bash
docker compose -f docker-compose.prod.yml exec ollama ollama list
```

### ドキュメントの取り込み

```bash
docker compose -f docker-compose.prod.yml exec api \
  python -c "from pathlib import Path; from src.infrastructure.ingestion.ingest_documents import run; run(Path('docs'))"
```

詳細は [`ドキュメント再取り込み手順.md`](ドキュメント再取り込み手順.md) を参照。

## 5. 既存システムと同居させるための設定

仕様書10.3の「LLM推論の負荷がWebアプリ本体を圧迫しないよう注意が必要」への対応。

### リソース制限

**CPU運用の場合、LLM推論はCPUコアを使い切る。** 制限しないと購買システム本体の応答が悪化する。
`docker-compose.prod.yml` の各サービスに上限を設定する。

```yaml
  ollama:
    image: ollama/ollama:latest
    deploy:
      resources:
        limits:
          cpus: "4.0"      # サーバの総コア数の半分程度から始める
          memory: 8G
```

```yaml
  api:
    deploy:
      resources:
        limits:
          cpus: "2.0"
          memory: 6G       # BGE-M3が2つ常駐するため6GB程度は必要
```

> **注意**：`deploy.resources.limits` は `docker compose up` でも有効に働くが、
> Docker Composeのバージョンによっては無視される場合がある。
> 効いているかは `docker stats` で実際の使用量を見て確認すること。

### 稼働時間の制限

夜間バッチ（購買システムのBAT-001〜005）と競合させたくない場合は、
`restart: unless-stopped` を使ったうえで、cron等で夜間に停止・早朝に起動する運用も検討する。

```bash
# 例：22時に停止、7時に起動
0 22 * * * cd /opt/rag-support-system && docker compose -f docker-compose.prod.yml stop
0 7 * * * cd /opt/rag-support-system && docker compose -f docker-compose.prod.yml start
```

## 6. アクセス制限

**このシステムには認証機能が無い**（仕様書13章でスコープ外）。
社内ネットワーク内であっても、無制限に公開すべきではない。

| 方法 | 内容 |
|---|---|
| ファイアウォール | 8501番ポートへのアクセスを、運用チームのセグメントからのみ許可する |
| リバースプロキシ | 既存のnginx等がある場合、Basic認証を挟んで公開する |
| ポートを開かない | 8000・6333・11434 はホストへ公開しない（3.4の構成では8501のみ公開している） |

**将来、認証を追加する場合**は `src/interfaces/api/dependencies.py` の
`get_current_user_id()` のみを変更すればよい設計になっている（仕様書7.4）。

## 7. CPU運用時の性能について

GPUなしで運用する場合、応答速度は以下が目安になる（開発環境での実測値）。

| 項目 | 実測値 |
|---|---|
| プロンプト評価速度 | 約32トークン/秒 |
| 日本語の文字数換算 | 約1.34文字/トークン |
| 履歴を1,000トークン増やした場合の初回応答の遅延 | 約31秒 |

**参照文書5件＋履歴を含めると、最初の1文字が表示されるまで20〜60秒程度かかる。**
利用者には「回答が出るまで1分近くかかることがある」と事前に案内しておくことを推奨する。

速度が問題になる場合の選択肢：

| 対策 | 効果 | 副作用 |
|---|---|---|
| `TOP_K` を5から3へ減らす（`rag_service.py`） | プロンプトが短くなり高速化 | 検索の取りこぼしが増える可能性 |
| 履歴の往復数を5から3へ減らす（`HISTORY_TURNS`） | 同上 | 前の会話を踏まえた回答の精度が落ちる |
| より小さいモデルへ変更（`qwen3:4b` 等） | 大幅に高速化 | 日本語の回答精度が落ちる |
| GPUの導入 | 5〜10倍程度の高速化 | ハードウェア調達が必要 |

いずれも仕様書で確定した値の変更にあたるため、変更する場合は仕様書側も更新すること。

## 8. つまずきやすい点

| 症状 | 原因と対処 |
|---|---|
| ポートが使用中でコンテナが起動しない | 購買システム本体と衝突。1.4で確認し、3.4の `ports` を変更する |
| `Connection refused` でOllamaにつながらない | `docker-compose.override.yml` が残っていないか確認（3.2） |
| ビルド時にPyPIへ接続できない | オフライン環境。2.4のホイール持ち込みが必要 |
| 起動後、最初の質問だけ極端に遅い | BGE-M3の初回読み込み（約2.2GB×2）。2回目以降は速くなる（キャッシュ済み） |
| 購買システム本体が重くなった | LLM推論がCPUを占有している。5章のリソース制限を設定する |
| 質問しても必ず「関連する文書が見つかりません」 | ドキュメント未取り込み。4章の取り込みを実施する |
