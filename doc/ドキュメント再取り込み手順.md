# ドキュメント再取り込み手順（リセットと入れ直し）

取り込み済みのドキュメントをすべて破棄し、正規のドキュメントを新たに読み込み直す手順。

---

## 0. なぜ「リセット」が必要なのか

このシステムの取り込み処理（Ingestion）は、**毎回すべてを作り直すのではなく差分だけを処理する**
設計になっている（仕様書6.2）。仕組みは2つの部品でできている。

| 部品 | 役割 |
|---|---|
| `.ingestion_state.json` | 前回取り込みを実行した時刻を記録する。**この時刻より新しいファイルだけ**が処理対象になる |
| `file_path` メタデータ | Qdrant上の各チャンクに元ファイルのパスが記録されている。同じパスのファイルを取り込むと、古いチャンクを削除してから登録し直す（仕様書6.3） |

この仕組みには、**入れ替え時に困る落とし穴が3つ**ある。

### 落とし穴1：削除したファイルのチャンクは残り続ける

取り込み処理は「配置されているファイル」しか見ない。
`docs/` からファイルを消しても、Qdrant上のチャンクは消えない。
**古い文書の内容が検索結果に出続け、それを根拠に回答が作られる。**

### 落とし穴2：ファイル名を変えると内容が二重に登録される

古いチャンクの削除は `file_path` をキーに行う。
`旧仕様.md` を `新仕様.md` にリネームすると、新しいパスで登録される一方、
古いパスのチャンクは残る。**同じ内容が2重にヒットする。**

### 落とし穴3：古い更新日時のファイルは無視される

処理対象の判定はファイルの更新日時（mtime）で行う。
別の場所からファイルをコピーする際に更新日時が保たれる操作
（`cp -p`、zipの展開、共有フォルダからのコピーなど）を行うと、
**前回実行時刻より古いファイルと判定され、取り込まれない。**

**正規のドキュメントに入れ替えるときは、これら3つを避けるため、
まず全部消してから入れ直す（リセット）のが確実である。**

## 2. リセットする

### 2.1 【重要】消えるものと消えないものの確認

| 対象 | リセットで消えるか | 備考 |
|---|---|---|
| Qdrantのベクトルデータ（`documents` コレクション） | **消える** | 目的なので問題ない |
| `.ingestion_state.json` | **消える** | 目的なので問題ない |
| **会話履歴（`data/history.db`）** | **消えない** | 別の保存先（SQLite）のため影響を受けない |
| LLMモデル（`ollama_data`） | 消えない | 再ダウンロード不要 |
| Embeddingモデル（`hf_cache`） | 消えない | 再ダウンロード不要 |

> 会話履歴も消したい場合は、別途 `data/history.db` を削除する。
> ただし過去の会話は復旧できないため、通常は残しておくこと。

### 2.2 古いドキュメントファイルを退避する

開発用のサンプル文書が `docs/` 配下に入っている。正規のドキュメントに入れ替えるため、
まず退避（または削除）する。

```bash
# 念のためバックアップを取ってから消す
mv docs docs_backup_$(date +%Y%m%d)

# 空のディレクトリ構成を作り直す
mkdir -p docs/specs docs/design docs/minutes docs/manuals
```

### 2.3 Qdrantのコレクションを削除する

```bash
python -c "
import urllib.request
req = urllib.request.Request('http://qdrant:6333/collections/documents', method='DELETE')
print('削除結果:', urllib.request.urlopen(req).status)
"
```

コレクションは、次の取り込み実行時に自動で作り直される（手動作成は不要）。

**本番環境の場合：**

```bash
docker compose -f docker-compose.prod.yml exec api python -c "（上記と同じ）"
```

### 2.4 取り込み状態ファイルを削除する

```bash
rm -f .ingestion_state.json
```

**この手順を飛ばすと、落とし穴3により新しいドキュメントが取り込まれないことがある。**
ファイルが無い場合、取り込み処理は「初回実行」と判断し、**すべてのファイルを対象にする。**

### 2.5 リセットできたか確認する

```bash
python -c "
import urllib.request, json
try:
    urllib.request.urlopen('http://qdrant:6333/collections/documents')
    print('コレクションがまだ存在します')
except Exception as e:
    print('コレクション削除済み（404が正常）:', e)
"
```

## 3. 正規のドキュメントを配置する

### 3.1 ディレクトリ構成の決まり

**`document_type`（文書種別）は、`docs/` の直下のディレクトリ名から自動判定される**（仕様書4章・5章）。
そのため、置く場所を間違えると検索の絞り込みが正しく動かない。

```
docs/
├── specs/       # 仕様書     → document_type = "specs"
├── design/      # 設計書     → document_type = "design"
├── minutes/     # 議事録     → document_type = "minutes"
└── manuals/     # マニュアル → document_type = "manuals"
```

ディレクトリ名は**この4つから変更しないこと。** UI側の絞り込み
（`ui/app.py` の `DOCUMENT_TYPES`）がこの名前と対応している。

サブディレクトリは作ってよい。`docs/specs/2026/発注管理.md` のように置いても、
`document_type` は1階層目の `specs` と判定される。

### 3.2 対応しているファイル形式

**現時点では `.md`（Markdown）のみが取り込まれる。**

| 拡張子 | 想定文書 | 対応状況 |
|---|---|---|
| `.md` | 仕様書 | **対応済み** |
| `.csv` | 議事録・Q&A集 | 未対応（実装TODO） |
| `.docx` | 設計書・マニュアル | 未対応（実装TODO） |
| `.xlsx` | 一覧表・パラメータ表 | 未対応（実装TODO） |

`.docx` や `.xlsx` を置いても**エラーにはならず、黙って無視される。**
取り込み後にチャンク数を確認して、想定した文書が入っているか必ず確かめること（5章）。

### 3.3 Markdownの書き方と検索精度の関係

チャンク分割は**見出し単位**で行われる（`MarkdownNodeParser`）。
そのため、見出しの付け方が検索精度に直結する。

| 推奨 | 理由 |
|---|---|
| `#`〜`###` で章・節を明示する | 見出しごとに1チャンクになり、検索の文脈が保たれる |
| 見出しに具体的な語を入れる（「4. エラーコード一覧」など） | 見出しは `chapter_title` としてメタデータに入り、回答のソース表示に出る |
| 1つの見出しの下を長くしすぎない | チャンクが大きいと、無関係な内容まで一緒にLLMへ渡される |
| 表（テーブル）はそのまま書いてよい | Markdownの表は分割されずチャンク内に残る |

### 3.4 ファイルを配置する

```bash
# 例：共有フォルダから正規ドキュメントをコピーする
cp /mnt/share/購買システム/仕様書/*.md docs/specs/
cp /mnt/share/購買システム/設計書/*.md docs/design/
```

> **`cp -p` や `rsync -a` は使わないこと。** 更新日時が保たれると落とし穴3に該当する。
> ただし2.4で `.ingestion_state.json` を削除していれば、この問題は起きない。

**本番環境（コンテナ）の場合**、`docs/` はホスト側のディレクトリを読み取り専用でマウントしている。
**ホスト側の `docs/` に置けばよく、コンテナ内へのコピーは不要**である。

## 4. 取り込みを実行する

### 開発環境（Devコンテナ内）

```bash
python -c "from pathlib import Path; from src.infrastructure.ingestion.ingest_documents import run; run(Path('docs'))"
```

### 本番環境

```bash
docker compose -f docker-compose.prod.yml exec api \
  python -c "from pathlib import Path; from src.infrastructure.ingestion.ingest_documents import run; run(Path('docs'))"
```

### 処理中に起きていること

```
① docs/ 配下の .md を列挙する（.ingestion_state.json が無いため全件が対象）
② 見出し単位でチャンクに分割する
③ メタデータを付ける（document_type / file_path / chapter_title / file_format / updated_at）
④ BGE-M3 でベクトル化する（dense と sparse の2種類）
⑤ Qdrant に登録する
⑥ 実行時刻を .ingestion_state.json に記録する
```

### 所要時間の目安

**④のベクトル化がほとんどの時間を占める。**
GPU環境なら1チャンクあたり0.1秒以下だが、CPU環境では1秒前後かかることがある。

| 文書量 | CPU環境の目安 |
|---|---|
| 45チャンク（開発用サンプル6本相当） | 1分程度 |
| 500チャンク | 10〜15分程度 |
| 2,000チャンク | 40〜60分程度 |

**途中で中断しないこと。** 中断すると、一部のファイルだけ登録された状態になる。
その場合は2章のリセットからやり直すのが確実である。

## 5. 取り込み結果を確認する

### 5.1 チャンク数と文書の一覧

1.1と同じスクリプトを実行する。**配置したファイルがすべて一覧に出ていること**を確認する。

```bash
python -c "
import urllib.request, json
from collections import Counter

req = urllib.request.Request(
    'http://qdrant:6333/collections/documents/points/scroll',
    data=json.dumps({'limit': 1000, 'with_payload': True, 'with_vector': False}).encode(),
    headers={'Content-Type': 'application/json'},
)
points = json.load(urllib.request.urlopen(req))['result']['points']
print(f'合計 {len(points)} チャンク')
print('文書種別ごと:', dict(Counter(p['payload'].get('document_type') for p in points)))
for path, n in sorted(Counter(p['payload'].get('file_path') for p in points).items()):
    print(f'  {n:3d}チャンク  {path}')
"
```

**確認するポイント**

| 確認内容 | 想定外だった場合 |
|---|---|
| 合計チャンク数が0でない | ファイルの配置場所か拡張子を間違えている（3.1・3.2） |
| 置いたファイルがすべて一覧にある | `.md` 以外のファイルは無視される（3.2） |
| 古い文書のパスが残っていない | リセットが不完全。2章をやり直す |
| `document_type` が4種類とも正しい | ディレクトリ名を確認（3.1） |

### 5.2 実際に質問して確かめる

ブラウザからUIを開き、**新しいドキュメントにしか書かれていない内容**を質問する。
正しく取り込めていれば、参照ソースに新しいファイルのパスが表示される。

古い文書の内容が返ってくる場合、リセットが不完全である。

### 5.3 関連度の閾値を見直す

回答が「関連する文書が見つかりませんでした」ばかりになる、
あるいは無関係な文書を根拠に回答する場合、**関連度の閾値が実際の文書に合っていない**可能性がある。

現在の閾値は開発用サンプル文書で測定した暫定値である（仕様書7.3対策3）。

```python
# src/application/rag_service.py
DENSE_RELEVANCE_THRESHOLD = 0.55
SPARSE_RELEVANCE_THRESHOLD = 0.12
```

正規のドキュメントを入れた後は、以下の手順で測り直すことを推奨する。

1. 文書に答えがある質問を5〜10問、答えが無い質問を5問程度用意する
2. 各質問について `dense` と `sparse` の生スコアを測る
3. 「答えがある質問群の最小値」と「無い質問群の最大値」の中間を閾値にする

測定用のスクリプト例：

```python
from src.application.rag_service import search
from src.infrastructure.qdrant_vector_store import DENSE_SCORE_KEY, SPARSE_SCORE_KEY

QUESTIONS = ["（ここに質問を並べる）"]
for q in QUESTIONS:
    nodes = search(q)
    d = max((n.node.metadata.get(DENSE_SCORE_KEY) or 0.0) for n in nodes) if nodes else 0.0
    s = max((n.node.metadata.get(SPARSE_SCORE_KEY) or 0.0) for n in nodes) if nodes else 0.0
    print(f"{q:40s} dense {d:.4f} / sparse {s:.4f}")
```

閾値を変更した場合は、仕様書7.3の記載も更新すること。

## 6. 一部のファイルだけ更新する場合（リセット不要）

**ドキュメントの内容を修正しただけなら、リセットは不要である。**
差分取り込みの仕組みがそのまま働く。

```bash
# ファイルを上書き保存してから、取り込みを実行するだけ
python -c "from pathlib import Path; from src.infrastructure.ingestion.ingest_documents import run; run(Path('docs'))"
```

更新日時が前回実行時刻より新しいファイルのみが処理され、
そのファイルの古いチャンクは削除されてから新しい内容で登録し直される（仕様書6.3）。

### リセットが必要なのはこのケース

| 状況 | リセットの必要性 |
|---|---|
| 既存ファイルの内容を修正した | **不要**（差分取り込みで対応） |
| 新しいファイルを追加した | **不要**（差分取り込みで対応） |
| ファイルを削除した | **必要**（落とし穴1。チャンクが残る） |
| ファイル名を変えた・移動した | **必要**（落とし穴2。二重登録される） |
| ドキュメント一式を別のものに入れ替える | **必要** |
| 更新日時が古いファイルをコピーした | **必要**、または `.ingestion_state.json` の削除のみでも可（落とし穴3） |

## 7. 困ったときの確認先

| 症状 | 確認すること |
|---|---|
| 取り込んでもチャンク数が0 | ファイルの拡張子（`.md` のみ対応）、配置ディレクトリ |
| 一部のファイルだけ入らない | 更新日時が古くないか。`.ingestion_state.json` を消して再実行 |
| 消したはずの古い内容が回答に出る | リセットが不完全。2.3のコレクション削除から実施 |
| 同じ内容が2件ヒットする | ファイル名変更による二重登録。2章のリセットで解消 |
| 取り込みが極端に遅い | CPU環境では正常（4章の目安を参照）。GPU環境なら`EMBEDDING_DEVICE`の設定を確認 |
| `Connection refused` が出る | Qdrantコンテナが起動しているか。`docker compose ps` で確認 |
