# RAG・LLM基礎知識メモ

このプロジェクトの実装過程で出てきたRAG・LLM関連の概念を、初学者向けにまとめたもの。
`doc/仕様書.md`が「何を作るか」、`実装手順.md`が「何を作ったか」だとすると、このファイルは「なぜそう作るか」の背景知識にあたる。

---

## 1. RAGとは何か

RAG（Retrieval-Augmented Generation、検索拡張生成）は、LLMに「関連する社内文書」を検索して渡してから回答させる仕組み。

**なぜLLM単体では不十分か**
- LLM（Qwen3など）は学習時点の一般知識しか持っていない。購買システムの仕様書や議事録のような社内文書の内容は知らない
- 知らないことでも、もっともらしい文章を生成してしまう傾向がある（ハルシネーション）

**RAGの基本フロー**（このプロジェクトでの実際の流れ）
```
質問文
  ↓
① Embeddingモデル（BGE-M3）で質問文をベクトル化
  ↓
② Qdrant（ベクトルDB）に格納済みの文書チャンクの中から、似ているものを検索
  ↓
③ 検索結果（該当チャンクの本文）を「参照文書」としてLLMへのプロンプトに埋め込む
  ↓
④ LLM（Qwen3 8B）が、渡された参照文書だけを根拠に回答を生成
```

ポイントは、LLM自体を再学習させているわけではなく、**質問のたびに関連文書を検索して、その場でプロンプトに詰め込んでいる**だけという点。これにより、LLMの学習後に追加されたドキュメントにも対応できる（Ingestionし直せば即座に反映される）。

## 2. Embeddingとベクトル検索

**Embeddingとは**
テキストを固定長の数値ベクトルに変換したもの。意味が近い文章ほど、ベクトル空間上で近い位置になるように学習されている。このプロジェクトでは`BGE-M3`というモデルを使っており、1つのテキストが1024次元のベクトル（dense）に変換される。

**Dense embedding（密ベクトル）**
- 1024次元の実数ベクトル。意味的な近さを捉える
- 例：「発注」と「オーダー」のような、表記が違っても意味が近い語を拾える

**Sparse embedding（疎ベクトル）**
- トークンID → 重み、のペアの集合（ほとんどの次元が0なので「疎」）。BM25（キーワード検索）に近い性質
- 完全一致・固有名詞に強い
- 実際に確認した出力例（`sparse_doc_vectors()`のテストより）：
  ```
  indices: [6, 26931, 43415, 199187, 104917, ...]  ← トークンID
  values:  [0.004, 0.263, 0.189, 0.204, 0.161, ...] ← 重み
  ```

**なぜハイブリッド検索（dense + sparse）にしたか**
denseのみだと、「エラーコードE1234」のような固有名詞・型番の完全一致検索が苦手なことがある（意味的には近いが表記が違う文章の方がスコアが高くなってしまう場合がある）。sparseを組み合わせることで、こうした完全一致が重要な検索語にも対応できる（`仕様書.md` 8章）。

実際に`search()`のテストで、「エラーコードE1234について教えて」という質問に対し、E1234を含むチャンクがスコア1.0（最上位）、無関係なチャンクがスコア0という結果になり、ハイブリッド検索が機能していることを確認した。

## 3. チャンク分割の考え方

文書全体を1つのベクトルにしてしまうと、
- 関係ない部分の情報でノイズが増え、検索精度が落ちる
- LLMに渡すコンテキストが無駄に長くなる

という問題があるため、文書を「チャンク」という小さな単位に分割してから、チャンクごとにEmbeddingを作る。

このプロジェクトでは**見出し単位**（Markdownの`#`/`##`など）で分割している（`MarkdownNodeParser`を使用）。実際にテストした際、以下のように親見出しと子見出しが別々のチャンクになることを確認した。

```markdown
# サンプル仕様      ← チャンク1（このセクション本文のみ）

本文テキストです。

## 詳細            ← チャンク2（別チャンク。親の本文は含まない）

詳細な内容。
```

こうすることで、文書の構造（章・節）を保ったまま、検索時に「関連する節だけ」をピンポイントで取得できる。

## 4. LLMのストリーミング応答

ChatGPTのように、回答が1文字ずつ（正確には数トークンずつ）表示されていく仕組み。ユーザーが「生成の完了を待たされている感」を減らすための表示方法。

**`delta`と`message.content`の違い**（実際に検証した内容）

ストリーミングAPI（`astream_chat`）は、生成の途中経過を何度もイベントとして返してくる。1回のイベント（`ChatResponse`オブジェクト）には主に2つの持ち方がある。

| フィールド | 中身 |
|---|---|
| `chunk.message.content` | **その時点までの全文**（毎回、今まで生成した分すべてが入っている） |
| `chunk.delta` | **今回新しく増えた部分だけ**（差分） |

実際にテストした結果：
```python
deltas = []
async for chunk in stream:
    deltas.append(chunk.delta)
print(''.join(deltas))  # → 生成された全文と完全一致
print(len(deltas))      # → 477（＝477回のイベントに分かれていた）
```

もし`chunk.message.content`をそのまま毎回クライアントに送ってしまうと、「今までの全文」を477回重複して送ることになり、帯域の無駄になる上、表示側（Streamlitの`st.write_stream`など）は「追記」を前提にしているため表示が壊れる。**`delta`だけを送り、クライアント側は受け取った断片を順番に末尾へ追記していく**、というのが正しい設計。

**NDJSON形式での配信**（`仕様書.md` 7.2で確定した方式）
1行1JSONで、最初にソース情報、以降はトークン差分を送る。
```json
{"type": "sources", "sources": [{"file_path": "...", "chapter_title": "...", "score": 0.62}]}
{"type": "token", "content": "参照"}
{"type": "token", "content": "文書に"}
{"type": "token", "content": "よると"}
...
```
ソースは検索（Qdrantへのクエリ）が完了した時点で確定しており、これはLLMの生成が始まる**前**に分かっている。そのため、生成を待たずに先頭行で送ってしまえる。

## 5. ハルシネーション対策の考え方

LLMは「それらしい文章」を作るのが得意なので、知らないことでも自信満々に間違った回答をすることがある（ハルシネーション）。このプロジェクトでは3段構えで対策する方針（`仕様書.md` 7.3）。

1. **システムプロンプトによる誘導**
   「参照文書の情報のみを根拠にせよ」「分からなければ『分かりません』と答えよ」と明示的に指示する。
   ただし、これは**プロンプトによる"お願い"に過ぎず、100%守られる保証はない**（LLMが指示を無視することもある）。だからこそ次の対策と組み合わせる。

2. **ソースの明示**
   回答と一緒に、参照した文書のファイル名・章タイトルを必ず表示する。LLMの回答を鵜呑みにせず、利用者が元文書を確認して裏取りできるようにする、という「人間側のセーフティネット」。

3. **類似度スコアの閾値チェック**（現時点では未実装・TODO）
   検索でヒットしたチャンクのスコアが低すぎる（＝そもそも関連する文書が無かった）場合に、LLMに無理に答えさせず「関連情報が見つかりませんでした」と返す仕組み。実際に`search()`のテストでは、無関係なチャンクのスコアが`0.0`近くになることを確認済みなので、将来この値を使って足切りできる見込み。

## 6. 今回使った技術要素の用語集

| 用語 | 役割 |
|---|---|
| **LlamaIndex** | RAGパイプラインを組み立てるためのPythonフレームワーク。チャンク分割・Embedding呼び出し・ベクトルDB連携・LLM呼び出しを統一的なAPIで扱える |
| **Qdrant** | ベクトルDB（ベクトル類似度検索に特化したデータベース）。dense/sparse両方のベクトルとメタデータをまとめて格納・検索できる |
| **BGE-M3** | 中国のBAAIが公開している多言語対応Embeddingモデル。dense/sparse両方を出力できるのが特徴（このプロジェクトのハイブリッド検索の要） |
| **FlagEmbedding** | BGE-M3のsparseベクトルを取得するための専用ライブラリ。LlamaIndexの標準Embedding連携はdenseのみ対応のため、sparse部分だけ別途このライブラリを使っている |
| **Ollama** | LLM（言語モデル）をローカル/セルフホストで動かすための実行基盤。モデルのダウンロード・量子化管理・APIサーバー機能を提供 |
| **Qwen3 8B** | Alibaba発のオープンLLM。8Bはパラメータ数（約80億）。`Q4_K_M`は4bit量子化の一種で、精度を多少落とす代わりにモデルサイズとメモリ使用量を抑える方式 |
| **uv** | Pythonのパッケージ・依存関係管理ツール（pipより高速）。このプロジェクトでは`pyproject.toml`でバージョンを`==`固定して管理している |
| **Hugging Face Hub** | 機械学習モデルの配布プラットフォーム。BGE-M3のモデル本体はここからダウンロードされ、`HF_HOME`で指定したキャッシュ先に保存される |
| **FastAPI** | PythonのWebフレームワーク。非同期処理・ストリーミングレスポンスと相性が良く、RAGServiceの結果をHTTP経由でStreamlitに渡す役割 |
| **Streamlit** | PythonでWeb UIを作れるフレームワーク。`st.write_stream`でストリーミング表示に対応できる |

## 7. コンテナ構成の基礎

このプロジェクトはdocker-composeで`api`（このDevコンテナ）・`qdrant`・`ollama`の3コンテナ構成になっている。

**コンテナは互いに隔離された別々のLinux環境**であり、あるコンテナにインストールされたコマンド（例：`ollama`コマンド）は、他のコンテナからは見えない。ただし、docker-composeの同じネットワークに属していれば、**サービス名をホスト名としてHTTP通信はできる**（例：`api`コンテナから`http://ollama:11434`）。

**Docker-outside-of-Docker（DooD）**
ホストのDockerソケット（`/var/run/docker.sock`）をコンテナ内にマウントし、コンテナ内の`docker`コマンドがホストの実際のDockerデーモンを直接操作する方式。`docker exec`でホスト上の兄弟コンテナ（`ollama`など）を操作できるようになる。

**Docker-in-Docker（DinD）**
コンテナの中に、まったく新しい独立したDockerデーモンを起動する方式。`--privileged`権限が必要で重い。しかも、この入れ子のデーモンはホストのdocker-composeネットワークとは別世界なので、**たとえ動いても`ollama`コンテナには到達できない**（DooDとの決定的な違い）。

このプロジェクトでは当初DinD・DooDの両方を試作したが、複雑さと過去のエラー（`moby install`失敗）を理由に撤回し、今はシンプルな`docker-compose.yml`直接参照の構成になっている（`実装手順.md` 0章参照）。そのため`api`コンテナからOllamaを操作する際は、`docker exec`ではなく**HTTP API（`/api/pull`など）を直接呼ぶ**方式を採用した。
